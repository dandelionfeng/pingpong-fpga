# 三人团队 GitHub 协作使用指南

适用项目：FPGA-AI 乒乓球发球判罚辅助系统；2026-09-19。

## 1. 先理解你们每天做什么

Git 在本机保存修改历史，GitHub 保存团队共享副本。commit（提交）只写入本机；push（推送）才上传。pull（拉取）更新本机。branch（分支）用于隔离任务；PR（Pull Request）是让队友检查并合并一个分支的申请。

main 保存可作为下一项任务起点的版本。三人各在自己的电脑、本地副本、任务分支里工作；不要共享一个 OneDrive 同步的 Git 工作目录。每天开始先更新，完成一个可说明的小步骤就提交，工作结束前推送任务分支。未完成也可推送并建立 Draft PR，标记不可合并。

分工：A（蒲公英）负责采集/FSIN/DDR/顶层；B 负责预处理/ROI/UDP；C 负责训练、RKNN、接收、几何及界面。B、C 先共同确认包格式；A、B 共同确认视频流握手与时钟域。目录归属是减少冲突的约定，不阻止跨目录协作。

## 2. 队长配置成员

仓库默认位置：`https://github.com/fengfengkang/pingpong-fpga`，以部署状态记录为准。仓库保持 Private。

队长打开仓库 Settings → Collaborators（组织仓库可能显示 Collaborators and teams）→ Add people，输入另两人的准确 GitHub 用户名。队友接受邀请后才能访问私人仓库。当前未提供两位队友账号，因此没有代发邀请。

随后把 `.github/CODEOWNERS` 改为实际负责人，例如 `/fpga/ @真实账号`、`/rk3566/ @真实账号`、`/vision/ @真实账号`。不要把示例文字直接当账号提交。CODEOWNERS 不是权限隔离，且自动请求评审和保护能力受套餐影响。所有有写权限的队员都要遵守评审约定。

GitHub Free 的私人仓库通常不支持受保护分支；Pro/Team 等计划支持的范围参见 [GitHub 官方说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。以部署记录中的实际 API 结果为准。若无法启用，不能声称 main 已有云端强制保护：本地 hook 只能防误操作，可被绕过，网页编辑和其他客户端不受它限制。不要为了保护分支擅自把竞赛仓库公开或购买套餐。

若账号支持保护，在 Settings → Branches 中保护 main：Require a pull request、至少 1 名其他队友批准、Require status checks（repository-checks）、禁止 force push 和删除。只有这些服务器规则实际生效，才是强制约束。

## 3. 每位队员首次配置（Windows）

安装 [Git for Windows](https://git-scm.com/download/win)、[Python 3](https://www.python.org/downloads/)；喜欢图形操作也可安装 [GitHub Desktop](https://desktop.github.com/)。在 GitHub 网页或客户端完成登录，不要把密码或访问令牌发给 AI。

选择普通本地目录，在 PowerShell 执行：

```powershell
git clone https://github.com/fengfengkang/pingpong-fpga.git
cd pingpong-fpga
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\bootstrap.ps1 -Name "你的名字" -Email "你的Git提交邮箱"
python -m unittest discover -s tests -v
```

邮箱可从 GitHub Settings → Emails 复制自己的 noreply 邮箱。不要使用队长邮箱冒充队长。初始化仅修改此仓库设置，安装提交前检查和禁止直接推送 main 的本地 hook；每次新 clone 都要执行。ExecutionPolicy Bypass 只用于这次脚本进程，不改变电脑全局策略。Linux/macOS 可使用 `git config --local core.hooksPath .githooks`，再自行设置 Git 姓名、邮箱及 `pull.ff only`。

队长当前目录已经是本地仓库，不要在其中重复 clone。队长的 Git 身份使用 fengfengkang 及对应 noreply 邮箱。GitHub CLI 安装在 `%LOCALAPPDATA%\Programs\GitHubCLI-portable\bin\gh.exe`；如未加入 PATH，可用完整路径执行。普通日常操作不依赖 CLI，网页即可创建 PR。

## 4. 每次开发的完整例子

以下示例是 A 开发 FSIN；B/C 换成自己的任务名。先保存未提交工作，`git status` 应显示工作区干净，再开始：

```powershell
git switch main
git pull --ff-only
git switch -c feat/a-fsin
```

现在让自己或 AI 修改该分支里的文件。任务要小，例如“生成可配置 FSIN 脉冲并给出仿真”，不要一项任务包含整个前后端。完成后：

```powershell
git status
git diff
git add fpga/rtl/capture/你的模块.sv fpga/sim/你的测试.sv
git diff --cached
python tools/check_repo.py --staged
git commit -m "feat(fpga): add FSIN generator and simulation"
git push -u origin feat/a-fsin
```

示例文件名须替换为真实文件。优先明确列出文件，不习惯 Git 时不要盲目 `git add .`。检查通过后还要运行本任务所需的仿真/算法测试；这里的 Python 检查不检查电路功能。

打开 GitHub 仓库 → Pull requests → New pull request，base 选 main，compare 选任务分支。填写自动出现的模板，写清目的、接口变化、实际测试和未验证项，指定另一位队友评审。评审人查看 Files changed 和 Checks，提出问题；作者在同一分支继续 commit、push，PR 会自动更新。检查通过且队友同意后，使用 Squash and merge，再删除远端任务分支。

合并后回到本机：

```powershell
git switch main
git pull --ff-only
git fetch --prune
```

下一个任务从新的 main 建新分支。Squash 合并后本地旧分支可能不会被 `git branch -d` 视为已合并；先保留即可，不为清理界面强制删除尚未核对的分支。

GitHub Desktop 用户可用 Fetch/Pull、New branch、Changes、Commit、Publish/Push、Create Pull Request 完成同样流程；终端检查仍应执行。本指南的流程依据 [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow)。

## 5. 同时改动与冲突处理

每天开工和较长任务合并前同步 main。先提交自己当前分支上的修改，再执行：

```powershell
git fetch origin
git merge origin/main
```

没有冲突时正常测试并推送。有冲突时 `git status` 会列出文件；打开文件，和原作者确认应保留的逻辑，删除 `<<<<<<<`、`=======`、`>>>>>>>` 标记并形成完整正确代码。然后 `git add 冲突文件`、`git commit`、测试、`git push`。看不懂时可以用 `git merge --abort` 取消本次合并，并找队友共同处理；开始合并前保持干净工作区。不要不看内容就选择“全部使用我的/对方的”。

接口文件、顶层约束和大型规划文档应指定当日编辑人。Word/PDF 无法像代码一样自动合并：Word 同时只允许一人编辑，其他人通过 Issue/PR 提意见。实现事实与接口以 Markdown 为主，阶段性同步 Word；现有 Word 与 Markdown 不由工具自动覆盖。

若已合并代码有错误，从最新 main 新建 `fix/...` 分支，通过 `git revert 错误提交号` 生成撤销提交，测试后走 PR。撤销 merge commit 的参数不同，先找队长确认。不要对共享历史使用 `reset --hard` 或强制推送。

## 6. 三人和多个 AI 如何配合

优先使用不同电脑的独立 clone。若同一台电脑开多个 agent，每个 agent 使用不同 worktree，不能同时切换同一工作目录的分支。例如在队长仓库内：

```powershell
git fetch origin
git worktree add -b feat/b-roi ..\pingpong-b-roi origin/main
git worktree add -b feat/c-receiver ..\pingpong-c-receiver origin/main
```

让 B 的 agent 只打开 `..\pingpong-b-roi`，C 的 agent 只打开 `..\pingpong-c-receiver`。不要把另一个任务的未提交改动复制过去。交接时记录实际提交号与分支。跨 worktree 的 Git 仓库配置通常共享，但文件和索引独立。

把 `handoffs/TEMPLATE.md` 复制成自己的任务记录，明确允许改哪些文件、输入输出样例、验收命令、硬件条件。其他工具未必自动读取 AGENTS.md，需要明确把该文件及相关契约交给它。

节省 Codex 额度的分配建议：

| 工作 | 推荐安排 | 验收人 |
|---|---|---|
| 文档整理、学习说明、独立测试向量、已冻结接口下的小模块草稿 | 其他 agent 或本地模型 | 对应模块负责人 |
| RTL 初稿与测试台 | 任一擅长代码的 agent，小任务交付 | A/B 看波形、综合与时序 |
| 数据处理、训练配置、几何单元测试、GUI 局部功能 | 其他 agent 可承担 | C 跑真实样本 |
| 协议冲突、跨 FPGA/Linux 集成、难复现故障、最终回归 | 集中用 Codex，提供最小复现和日志 | 涉及的两位负责人 |
| 接线、示波器测同步、烧录、板卡性能测试与最终判定 | 人操作，AI 辅助分析 | 团队共同签字确认 |

不要让多个 agent 重复实现同一个模块来“自动加速”，也不要把 AI 自述当测试报告。每个 PR 至少由一个非作者的人阅读。把可重复的检查写进脚本并在本机执行，通常比让模型反复阅读全仓库更省额度。

## 7. 自动检查、产物与阶段版本

每个 PR 和 main 推送运行 Repository checks：冲突标记、部分常见凭据、大文件/生成文件检查，以及检查器自身的测试。它不会综合 FPGA，也不会运行 NPU。初次上云后的实际运行结果见部署状态。检查器是基础防误传，不是完整安全扫描。

本地提交 hook 检查暂存区，推送 hook 禁止直接推送或删除 main。故意跳过 hook 会破坏约定；不要把绕过方法当日常操作。修改工具规则也应走 PR。GitHub Actions 使用托管 Linux runner，每次超时 5 分钟，只给内容读取权限；私人仓库消耗账户 Actions 配额，队长在 Billing/Actions 查看实际余额，不在此方案中自动开通付费服务。

RTL、约束、构建脚本、训练代码、配置、小测试向量进 Git；权重、视频、厂商 SDK、bitstream、综合中间目录不进普通历史。按 `artifacts/README.md` 留下 SHA256 和源码版本。不要修改忽略规则来强塞大文件。

每个稳定演示版本由队长在 GitHub Releases 选择对应 main 提交，使用有意义的版本标签（例如 v0.1.0-capture），写明已验收功能、已知问题、硬件环境和报告位置；标签不代表所有目标已完成。交付前冻结代码、权重与标定版本，保留旧版本便于复现。
