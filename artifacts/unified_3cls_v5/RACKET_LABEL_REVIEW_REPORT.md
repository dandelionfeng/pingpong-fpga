# RACKET_LABEL_REVIEW_REPORT — 球拍漏标复核（本轮结论：不注入、不伪造）

日期：2026-10-26

## 1. 复核对象

V3/V4 中新增的 **521 张 BNDSTT 球帧**（`ps_*`），其 ball 有标签、hand 有自动候选、
**racket 无标签**。数据：`artifacts/unified_3cls_v4/racket_candidates_ps521.csv`（521 行）。

## 2. Racket 专项模型复核结果（与实际输出一致）

| 桶 | 判据 | 帧数 | 说明 |
| --- | --- | ---: | --- |
| 高置信候选 | top ≥ 0.40 | **104** | 框存在，但**偏松**（含前臂/手部） |
| 待复核 | 0.20–0.40 | 82 | 有球拍嫌疑，位置不稳 |
| 不确定 | 0.05–0.20 | 125 | 几乎无法判断 |
| 无检出 | < 0.05 | 210 | 专项模型看不到球拍 |

## 3. 检查项逐条回答

| 检查 | 结果 |
| --- | --- |
| 球拍边界是否过松 | **是**。104 个候选框普遍大于球拍本体，明显包含前臂/手（见 `visuals/v4_added_racket_candidates.jpg`） |
| 是否包含手部或前臂 | **是**，这正是"过松"的成因 |
| 球拍侧面框是否合理 | 远景侧拍时框宽度估计偏差较大，IoU 低 |
| 是否误把背景物体当球拍 | 抽查未见明显误检（红框都落在球员挥拍区域） |
| 是否存在明显漏检 | **是**，210 帧"无检出"中很可能仍有真实球拍（远端小球拍） |
| 是否出现同一球拍多个重复框 | 105 框 / 104 帧，基本一对一，未发现重复 |

## 4. 两种自动修复方案的实测代价（关键）

| 方案 | 做法 | 实测结果 | 判定 |
| --- | --- | --- | --- |
| **注入**（V4 采用） | 把 104 帧的 105 个候选框写入训练集 | racket AP50 0.738→**0.726**，F1@0.25 0.758→**0.669**，FP 42→**71** | ❌ **拒绝**，已实测有害 |
| **隔离**（V4 也做了） | 把 207 帧歧义帧剔除训练 | ball GT 2,499→**2,292**（−207），且球召回未改善 | ⚠ 有代价，不能单独解决 racket |

**结论：自动标注既不能"补"也不能"删"出干净的球拍标签，必须人工。**

## 5. 本轮（V5）的处理

V5 训练数据 = **V3 数据原样**（`pingpong_unified_3cls_v4`，4,431 图），原因：

1. 本轮要验证的唯一变量是**训练分辨率 1280**，必须让数据保持不变，否则无法归因；
2. 前述两种自动修复都已被实测证明有代价，不重复使用；
3. 因此 **V5 仍带这个已知标注缺口**，已在报告与交付文档中声明。
