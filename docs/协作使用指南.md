# 三人团队 GitHub 使用指南

更新：2026-10-04。适用当前 AFH03 USB 同步双目自主命题方案，以及到货前的 PC 算法开发。仓库：[fengfengkang/pingpong-fpga](https://github.com/fengfengkang/pingpong-fpga)，保持 Private。

## 先理解每天要做什么

Git 保存本机修改历史，GitHub 保存团队共享副本。commit 只保存到本机，push 才上传；branch 是每项任务的独立工作线，PR 是供队友检查和合并的改动。main 保存经过蒲公英确认的共同起点。三个人在各自电脑的普通本地目录工作，避免共用一个 OneDrive 同步的 Git 工作目录。

先读[当前方案](../plans/current/README.md)和自己的个人说明。A（蒲公英）负责输入、缓存、软件参考、FPGA 前三级、硬件链路与系统集成；B 负责 FPGA 后四级与打包、CPU 球心、标定、三维和事件；C 负责数据、三类模型、PC 实际推理、导出和独立评分。角色详细实现以[总分工](../项目规划/AFH03_USB同步双目方案一个月分工/00_三人分工与一个月实施安排.md)和同目录个人文件为准。

一项任务明确要交付的文件和运行入口，完成可说明的一步就提交，再推送任务分支。未完成可以建立 Draft PR，交接时注明待做部分。需要其他模块配合时写清负责人、输入样例和依赖，目录约定用于减少冲突。

## 首次配置电脑

安装 Git、Python 3，并在 GitHub 网页或 GitHub Desktop 登录。个人模块使用的 C++17/CMake/OpenCV、Verilog/Icarus Verilog/TD、PyTorch/RKNN-Toolkit2 按个人说明安装并记录实际版本。Windows 可进行 PC 算法和 RTL 仿真，Linux 环境用于可移植构建及相应模型工具链；最终 V4L2、DDR3L、PCIe 和 NPU 运行在 AFH03 上验证。

选择普通本地目录，在 PowerShell 执行：

```powershell
git clone https://github.com/fengfengkang/pingpong-fpga.git
cd pingpong-fpga
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\bootstrap.ps1 -Name "你的名字" -Email "你的Git提交邮箱"
python -m unittest discover -s tests -v
```

邮箱从 GitHub Settings → Emails 复制自己的提交邮箱或 noreply 邮箱。初始化脚本仅设置此仓库的身份、换行和 hook；每次新 clone 都执行。上面的 ExecutionPolicy 仅针对该脚本进程。Linux 环境使用 `git config --local core.hooksPath .githooks`，自行设置提交身份和 `pull.ff only`。不要把账号密码、访问令牌或授权文件发给 agent。

蒲公英现有 `C:\FPGA competition` 已是本地仓库，无需重复 clone。GitHub CLI 便携位置为 `%LOCALAPPDATA%\Programs\GitHubCLI-portable\bin\gh.exe`，未加入 PATH 时可使用完整路径；网页和 Desktop 也能完成 PR 操作。

## 做一项任务的完整例子

以下以 A 实现文件输入为例。示例分支和源码文件表示计划中的实现，要替换为当前任务的真实名称。先查看 `git status`，保存已有工作，确保开始切换前工作区干净：

```powershell
git fetch origin
git switch main
git pull --ff-only
git switch -c codex/a-file-input
```

若依赖某个尚未合并的 PR，先核对该分支的提交，再以明确的依赖分支为基准，并在新 PR 中注明。不要混入另一个任务的未提交改动，也不要重置现有文件来得到干净目录。

修改、运行本任务检查后，明确列出要提交的文件：

```powershell
git status
git diff
git add -- software/pc_pipeline/file_frame_source.cpp tests/pc_pipeline/test_file_frame_source.cpp
git diff --cached
python tools/check_repo.py --staged
python -m unittest discover -s tests -v
git diff --cached --check
git commit -m "feat(pc): add file frame source"
git push -u origin codex/a-file-input
```

上述源码文件尚待任务创建。提交前还要运行相应输入/算法、仿真或模型检查，并保存真实日志。首次使用 Git 时优先逐个列出文件，确认没有厂商资料、视频、权重或生成工程混入。

在 GitHub → Pull requests → New pull request 中选择正确的 base 和任务分支。按模板写清目的、接口影响、实际检查、未验证项及交接入口。蒲公英阅读 Files changed、Checks 和结果后最终确认，可参考相关队友的技术复核建议；作者在同一分支继续提交，PR 自动更新。检查通过且蒲公英明确授权后用 Squash and merge 合并，不额外要求另一位队友点击 Approve。合并后回到本机同步：

```powershell
git switch main
git pull --ff-only
git fetch --prune
```

下一项任务从新 main 开始。Squash 合并后本地旧分支可能仍显示未合并，先核对内容再清理；不要为整理分支强制删除尚未确认的工作。GitHub Desktop 的 Fetch/Pull、New branch、Changes、Commit、Push、Create Pull Request 对应上述过程，必要的本地检查仍需执行。流程依据 [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow)。

## 如何一起修改和处理冲突

先提交自己的当前改动，再用 `git fetch origin`、`git merge origin/main` 同步最新 main。冲突出现后共同核对相关文件的语义，形成完整结果，再暂存、提交、验证和推送。无法判断时先取消本次合并并联系原作者；避免直接选择整份“我的”或“对方的”。共享历史不用 `reset --hard` 或强制推送清理。

当前接口评审重点是 `pair_id`、同眼前帧、取整和边界、Mask 位序、ROI 映射、模型输入、坐标系及异步结果生命周期。A/B 核对搜索图和运动前端，B/C 核对测量、检测框与事件，A/C 核对原图保留和异步调度。详见[接口入口](../项目规划/接口与验收契约.md)，评审完成前保留草案标记。

Word/PDF 同时指定一位编辑人；其他人通过差异说明提出意见。只有任务明确要求同步时才更新 Markdown 和 Word，保留原文件并核对内容。旧版本按[归档索引](../archive/README.md)保存原始字节和校验和，历史交接按原日期保留。

## 与 AI agent 配合

先把角色、当前目标、允许修改的文件、输入和交付内容交给 agent，要求它阅读[项目规则](../AGENTS.md)与 [AI agent 指南](AI_agent协作指南.md)，再复制个人职责文件末尾的对应提示词。agent 自主推进已授权任务，完成后交真实运行入口、结果和未解决项。

未经用户要求不自动启动其他 agent。已经授权并行时，各任务使用独立 clone 或 worktree，并限定文件范围。例如在干净工作区核对基准后：

```powershell
git fetch origin
git worktree add -b codex/b-motion-mask ..\pingpong-b-mask origin/main
git worktree add -b codex/c-pc-detector ..\pingpong-c-detector origin/main
```

每个 agent 只操作分配的目录；交接提交后，由集成人在自己的分支逐项复核。方案建议的 `software/pc_pipeline/` 等目录仍待实现，这些命令只创建工作副本。原理见 [Git worktree 官方文档](https://git-scm.com/docs/git-worktree)。

AI 给出的代码、波形解释或性能数字需实际复现；PC 回放、RTL 仿真、综合、RKNN 转换及正式上板分别记结果。纯检测框回放只验证下游，实际 PC 模型推理另验。完成任务按 [handoffs/TEMPLATE.md](../handoffs/TEMPLATE.md)留下交接。

## 成员、自动检查与大文件

队长在 Settings → Collaborators 中用队友的准确账号邀请成员，队友接受后可访问私人仓库。`.github/CODEOWNERS` 目前只登记队长；取得真实账号后再添加对应负责人，不能把角色字母或示例文字当作用户名。

本地提交 hook 检查暂存区，推送 hook 阻止直接推送或删除 main。PR 的 Repository checks 运行仓库文件检查及检查器测试，不执行 FPGA 综合或 NPU 推理。云端是否强制评审和检查以仓库 Settings 中实际生效的规则为准；本指南和本地 hook 不等于云端保护。分支保护适用范围见 [GitHub 官方说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)，保持现有私人仓库和服务配置。

2026-10-04 蒲公英明确要求所有审批由本人确认，现行流程按此执行。main 保留云端 PR、`repository-checks` 和最新 main 要求，管理员同样受约束，强制推送和删除仍禁止；强制批准评审数调整为 0。GitHub 不允许作者批准自己的 PR，见[官方说明](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)。最终审批在蒲公英的任务对话或 PR 明确确认中记录，云端负责强制检查；实际配置见[仓库分支设置](https://github.com/fengfengkang/pingpong-fpga/settings/branches)。

RTL、构建脚本、训练代码、配置和小型固定样例进入 Git。原始视频、厂商 SDK、权重、bitstream 和生成目录留在本地，按[产物说明](../artifacts/README.md)登记来源、许可、SHA-256、源码与工具版本。稳定版本的标记必须对应实际完成的范围，硬件结果增加板卡/相机、标定和运行日志。
